INSTRUCTIONS DE DÉMARRAGE — RÉSIDENCE BLUE
==========================================

Deux modes sont possibles :
- Mode A : deux serveurs séparés en local avec npm (API NestJS + Angular).
- Mode B : tout avec Docker Compose (PostgreSQL + migrations + API + Web).

Le mode B est le plus simple et le plus proche de la production.

----------------------------------------------------------------------
0. PRÉREQUIS
----------------------------------------------------------------------
- Node.js 22+ et npm 10+
- Docker Desktop avec conteneurs Linux (pour le mode B)
- PostgreSQL 16 accessible en local sur localhost:5432 si tu choisis le
  mode A hors Docker (la base du docker-compose n'expose PAS de port à l'hôte)

----------------------------------------------------------------------
1. CONFIGURATION DES VARIABLES D'ENVIRONNEMENT
----------------------------------------------------------------------
À la racine du projet :

  PowerShell :  Copy-Item .env.example .env
  Bash/macOS :  cp .env.example .env

Remplace TOUTES les valeurs "changeme_..." dans .env par des secrets forts :

  node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # ENCRYPTION_MASTER_KEY

Ne jamais committer .env.

Important :
- Le .env de la RACINE est utilisé par Docker Compose et par les scripts npm
  lancés depuis la racine (seed, migration, sauvegarde).
- Quand l'API est lancée avec npm, elle lit apps/api/.env (ConfigModule part
  du dossier apps/api). Vérifie au minimum :
    NODE_ENV, PORT, DATABASE_URL, ENCRYPTION_MASTER_KEY, JWT_SECRET.
  DATABASE_URL doit pointer vers ton PostgreSQL local, par exemple :
    postgresql://app_user:<mot_de_passe>@localhost:5432/residence_blue_db?schema=public

----------------------------------------------------------------------
2. MODE A — LES DEUX SERVEURS EN LOCAL (npm)
----------------------------------------------------------------------
Depuis la racine, une seule fois :

  npm install
  npm run prisma:generate
  npx prisma migrate deploy --schema=apps/api/prisma/schema.prisma
  npm run build
  npm run seed        # facultatif mais recommandé la 1re fois (chambres + comptes)

Puis ouvre DEUX terminaux à la racine du projet.

Terminal 1 — API NestJS (port 3000) :

  npm run start:dev --workspace=@residence-blue/api

  (ou `npm run start --workspace=@residence-blue/api` sans watch)

Terminal 2 — Application Web Angular PWA (port 4200) :

  npm run start --workspace=@residence-blue/web

URLs :
- Application :        http://localhost:4200
- API :                http://localhost:3000
- Santé API :          http://localhost:3000/health
- Santé API (préfixe): http://localhost:3000/api/health

Le serveur Angular proxifie /api et /health vers http://127.0.0.1:3000
(voir apps/web/proxy.conf.json) : gestion des tokens et SSE fonctionnent
sans configuration supplémentaire.

Arrêt : Ctrl+C dans chaque terminal.

Compte directrice créé par le seed (développement uniquement, à changer
immédiatement hors local) : aissatou.ba@residenceblue.sn / ThiesTeranga2024!

----------------------------------------------------------------------
3. MODE B — DOCKER COMPOSE (RECOMMANDÉ)
----------------------------------------------------------------------
Depuis la racine, avec .env renseigné :

  docker compose up -d --build db migrate api web

Services lancés :
- db       : PostgreSQL 16, réseau interne uniquement, aucun port publié
- migrate  : applique les migrations Prisma puis s'arrête
- api      : NestJS sur http://localhost:3000
- web      : Nginx sur http://localhost:4200

Vérification :

  docker compose ps
  docker compose logs -f api web
  curl http://localhost:3000/health

Si la base est neuve et que tu veux le jeu de données initial :

  docker compose exec api npx ts-node --project tsconfig.json prisma/seed.ts

Remarque : le service "backup" du compose de développement n'est pas inclus
dans la commande ci-dessus. Son script exige BACKUP_OFFSITE_DIR, qui n'est pas
encore transmis dans docker-compose.yml : sans montage hors site il redémarre
en erreur. Ne l'ajoute que lorsque cette configuration sera corrigée.

Commandes utiles :

  docker compose restart api web          # redémarrer après un changement
  docker compose up -d --build api web    # reconstruire après un changement de code
  docker compose down                     # arrêter en gardant les données
  docker compose down -v                  # ATTENTION : supprime aussi les volumes DB

Après l'ajout d'une migration :

  docker compose run --rm migrate

----------------------------------------------------------------------
4. MODE PRODUCTION (serveur avec DNS)
----------------------------------------------------------------------
Renseigner HTTPS_DOMAIN, COOKIE_SECURE=true et BACKUP_OFFSITE_DIR dans .env,
puis :

  docker compose -f docker-compose.prod.yml up -d --build

Le proxy Caddy publie 80/443 et termine le TLS. L'API et le Web ne publient
aucun port directement. Utilise le même -f pour ps/logs/down :

  docker compose -f docker-compose.prod.yml ps
  docker compose -f docker-compose.prod.yml logs -f api web proxy

----------------------------------------------------------------------
5. DÉPANNAGE RAPIDE
----------------------------------------------------------------------
- "Port 3000 déjà utilisé" : change PORT dans .env (mode npm) ou arrête le
  service qui occupe le port.
- /health répond mais l'écran affiche des erreurs /api : vérifie que l'API
  tourne et que le proxy Angular cible bien 127.0.0.1:3000.
- Erreur Prisma "table does not exist" : la migration n'a pas été appliquée
  (`npx prisma migrate deploy --schema=apps/api/prisma/schema.prisma` ou
  `docker compose run --rm migrate`).
- 403 sur toutes les routes : compte sans droits ou seed non exécuté ;
  vérifier starterProfile/screenAccess du compte connecté.
- Sous Windows, si `cp` n'existe pas, utiliser Copy-Item comme indiqué plus haut.
